# 03 Response Format / 回答格式

本文件定义 Agent 如何把 05 返回的检索结果展示给业务员。

核心原则：

> 内部可以结构化，外部必须业务化。

不得把 `Product_SKU / Factory_Offer / Exact_Match / Unmet_Conditions` 等内部字段原样堆给业务员。

---

## 一、默认使用“产品卡片式”结果

每个推荐结果优先按以下顺序展示：

1. 产品图片
2. SKU + 简短定位
3. 核心供应信息
4. 产品特性 / 性能
5. 推荐原因
6. 必要提醒

### 必须优先显示产品图片

如果 `Main_Image` 可访问：

- 直接展示图片；
- 不要只输出 `main.jpg` 文件名；
- 多个推荐产品时，每个 SKU 对应显示自己的主图。

如果平台无法直接渲染图片：

- 给出可访问的图片路径或文件引用；
- 明确说明当前平台未能直接展示图片；
- 不得假装图片已经显示。

---

## 二、业务员默认看到的内容

推荐结果建议展示：

```text
【产品图片】

SKU：F0228
适合：日常 / 长距离行走

工厂：富置高
材质：PU
详细材质：绿色网布 + 高回弹 PU Foam + 蓝色 PU Gel
尺码：XS–XL
MOQ：3000 双
参考价格：¥6.9

产品特点：
- 透气排湿
- 缓震
- 回弹
- 轻度足弓支撑

性能：
缓震 3 / 回弹 4 / 软硬 3

为什么推荐：
- 价格满足客户预算
- 回弹较好，适合日常舒适型需求
- 软硬适中，不会过软
- 轻度足弓支撑，适合一般舒适需求

注意：
- 如果“日常”场景尚未正式确认，应写“场景标签待确认”
```

---

## 三、禁止默认展示内部技术字段

以下内容默认不直接展示给普通业务员：

```text
Product_SKU:
Factory_Offer:
Match_Reasons:
Unmet_Conditions:
Exact_Match:
Search_Request:
Hard_Conditions:
Soft_Conditions:
```

这些字段保留在系统内部。

只有用户明确要求“看检索依据 / 看内部匹配条件 / 看原始结果”时才展示。

---

## 四、多产品推荐

如果命中多个产品：

- 优先展示 3～5 个；
- 每个产品单独成块；
- 每块都有图片 + 核心参数 + 推荐原因；
- 不要先输出一大段总技术分析再让业务员自己找重点。

推荐开头可以直接写：

```text
我找到 3 款比较符合的，先看这 3 款：
```

然后依次展示产品卡片。

---

## 五、同一 SKU 多工厂

如果同一 SKU 有多个 Factory Offer：

- 产品图片只需展示一次；
- 在同一个产品块内列出不同工厂方案；
- 清楚区分各工厂的 Price / MOQ / Material / Size；
- 可以说明哪个供应方案更符合本次需求；
- 不得把多个工厂数据混成一个报价。

---

## 六、非完全匹配

如果没有完全满足全部条件：

不要输出：

```text
Exact_Match = false
Unmet_Conditions = ...
```

改成业务语言：

```text
这个款式最接近你的要求，但有一点需要注意：
- 你要求 MOQ ≤ 1000，这个工厂 MOQ 是 1500。
```

如果只是某个软条件或尚未确认的场景标签：

```text
补充说明：
- 产品性能符合，但“日常”场景标签目前还没有正式确认。
```

---

## 七、回答原则

1. 图片优先于长文字。
2. 参数优先于系统字段名。
3. 推荐原因必须直接对应用户本次需求。
4. 必要缺口要说明，但不要输出系统调试信息。
5. 不自行更改 SKU、Factory、Price、MOQ。
6. 不重新排序 04 已确定的候选。
7. 根据用户问题适当精简字段，但不能隐藏会影响业务判断的重要冲突。
8. 产品查询回答应像业务产品推荐，不像数据库调试日志。
