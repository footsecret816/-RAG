# 06 索引存储与运行方式

本文件定义真实检索索引如何存放，以及在不同运行平台中如何保持可迁移。

核心原则：

> GitHub 保存规则和代码；真实产品数据、关键词索引和向量索引全部保存在公司自己的数据目录。

---

## 一、推荐目录

```text
Product_Data/
├─ Product_KB/
│  └─ 真实产品资料
│
└─ Search_Index/
   ├─ records/
   ├─ keywords/
   ├─ vectors/
   └─ index_meta/
```

说明：

### records

保存：

- 产品检索记录
- 产品货号
- 工厂报价
- 结构化字段
- 产品主图引用
- 包装货号引用

### keywords

保存：

- 自动提炼关键词
- 标准词映射
- 每条检索记录对应的关键词集合

### vectors

保存：

- 产品向量
- 向量记录标识
- 向量模型版本
- 与产品检索记录的对应关系

### index_meta

保存：

- 索引版本
- 最后构建时间
- 向量模型信息
- 数据版本
- 待更新记录
- 索引健康状态

---

## 二、GitHub 不保存什么

以下内容不得提交到 GitHub：

- 真实产品货号数据
- 产品图片
- 工厂报价
- 真实价格
- 起订量
- 客户信息
- 产品关键词索引
- 产品语义检索文本
- 产品向量
- 向量索引文件
- 本地业务数据路径中的敏感内容

GitHub 只保存：

- 规则
- 字段定义
- 自动提炼逻辑
- 检索逻辑
- 排序逻辑
- 索引更新逻辑
- 平台适配说明

---

## 三、为什么索引单独存放

产品知识库是真实数据源。

搜索索引是为了提高检索效率生成的副本。

所以：

```text
Product_KB
= 真源

Search_Index
= 可删除、可重建的派生数据
```

如果索引损坏：

```text
删除 Search_Index
↓
重新读取 Product_KB
↓
重新生成
```

不会影响真实产品资料。

---

## 四、前期不强制使用大型向量数据库

当前产品规模如果只有几百到几千条检索记录：

- 可以先使用轻量本地向量索引；
- 不需要一开始就部署复杂服务器；
- 不把系统绑定在某一种向量数据库上。

核心接口只需要支持：

```text
写入向量
更新向量
删除向量
按查询向量取最相近候选
```

未来换成更专业的向量数据库时，上层业务规则不需要重写。

---

## 五、运行平台与索引解耦

目标结构：

```text
Accio / 其他 Agent 平台
↓
产品检索 Skill
↓
04 检索引擎
↓
本地 Product_KB + Search_Index
```

平台只负责调用。

真实索引不应该永久依赖某一家 Agent 平台内部知识库。

---

## 六、索引加载

系统启动或 Skill 首次执行时：

```text
检查 Product_KB
↓
检查 Search_Index 是否存在
↓
检查索引版本
↓
检查是否存在待同步变更
↓
可用 → 直接加载
不可用 / 版本过旧 → 重建或增量更新
```

---

## 七、索引状态

建议至少记录：

```text
正常
待更新
重建中
向量缺失
异常
```

如果向量缺失：

- 仍允许结构化 + 关键词检索；
- 不影响基本查询；
- 后续补建向量。

---

## 八、向量服务接口保持可替换

04 不应把某一个具体向量模型或数据库写死在业务规则中。

应保持：

```text
产品语义文本
↓
向量生成接口
↓
向量

查询语义文本
↓
同一向量生成接口
↓
查询向量

查询向量
↓
向量检索接口
↓
相似候选
```

以后无论更换：

- 本地模型
- 云端向量接口
- 向量数据库
- Agent 平台

核心产品规则都不需要改变。

---

## 九、数据备份原则

需要重点备份：

```text
Product_KB
```

Search_Index 可以备份，但不是最重要资产，因为可以重建。

真正不能丢的是：

- 标准化后的产品资料
- 产品图片
- 工厂报价资料
- 已人工确认的信息

---

## 十、核心原则

1. 产品资料和索引数据不进入 GitHub。
2. 产品知识库是真源，索引只是派生层。
3. 前期优先轻量本地索引，不提前复杂化。
4. 向量模型和向量数据库必须可替换。
5. 向量失败时基础检索仍然能运行。
6. 换平台时优先迁移 Skill 和数据目录，不重做业务规则。
